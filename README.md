# Agent Project Governance

`agent-project-governance` 是一套面向 AI Agent 协作开发的项目治理 skill。它帮助项目建立一套 Agent 能找到、能执行、能验证、能持续修正的工程规则。

它解决的不是“多写几份文档”，而是以下实际问题：

- Agent 开始修改前不知道必须先读什么，容易破坏已有约束或混入无关修改。
- 需求、技术债、迭代记录、重大决策和故障经验散落在不同文件中，后续 Agent 找不到权威来源。
- 文档声明流程已经存在，但实际缺文件、断链接、命令过期或与当前代码冲突。
- 项目曾经踩过坑，却没有把教训转化为下次必须执行的检查。

本 skill 不会把某个参考项目的全部流程照搬到目标仓库。它会先读取项目真实情况，再只建立与该项目工作方式和风险相符的治理能力。

## 适合谁使用

以下情况适合使用本 skill：

| 场景 | 使用目标 |
| --- | --- |
| 新项目准备让 Agent 参与开发 | 建立最小但可靠的工作入口、验证和经验反馈机制 |
| 持续开发的产品项目已有零散规则或文档 | 将有效内容收敛到标准结构，避免 Agent 到处猜规则 |
| 项目已经有 `AGENTS.md` 或治理目录 | 审计结构是否真的可用，识别缺失或过期内容 |
| 发生回归、部署故障、安全遗漏或反复返工 | 把原因转化为可复用的门禁、SOP 或经验记录 |
| Agent 需要提交、发布、调用外部服务或处理高风险功能 | 明确验证证据和额外安全约束 |

如果任务只是一次性的小改动，且 Agent 不会长期参与维护，不一定需要完整的产品治理结构；本 skill 会建议较轻的协作规则，而不是制造流程负担。

## 你会得到什么

执行后的具体结果取决于项目情况，但通常包括：

| 结果 | 作用 |
| --- | --- |
| `AGENTS.md` | Agent 的启动入口：必须遵守的约束、任务路由、活跃陷阱和收尾检查 |
| `.agent-governance/manifest.yaml` | 治理能力清单与状态记录，用于判断哪些能力已具备、缺失或失效 |
| `EVOLUTION.md` | 问题速查与经验写回位置，避免重复踩坑 |
| `docs/README.md` | 文档地图，告诉人和 Agent 每类事实或流程应去哪里找 |
| `docs/sop/` | 可重复执行的流程，例如测试、Git、需求进入、迭代、变更控制和发布 |
| `docs/reference/` | 当前有效且相对稳定的技术事实，例如架构入口、配置边界和依赖约束 |
| `docs/backlog/` 与 `docs/iterations/` | 可执行工作项、验收标准、当前推进记录和验证证据 |
| `docs/decisions/` | 重大取舍记录，说明为何选择当前方案 |
| `docs/roadmap/` 与 `docs/proposals/` | 阶段方向与尚未进入实施的候选想法 |
| 本 skill 内置校验器 `scripts/validate_project_governance.py` | 检查目标项目治理产物的一致性 |

关键原则是：存在文件不等于具备能力。只有文件内容准确、入口可到达、命令可执行且状态不矛盾，相关治理能力才算有效。

## 工作方式

### 1. 先检查现状

Agent 会先读取仓库，而不是先生成模板。检查内容包括：

- 技术栈、构建工具、测试命令和交付方式；
- 是否有认证、权限、数据库、部署、外部调用或其他高风险边界；
- 是否已有 `AGENTS.md`、需求池、迭代、ADR、测试/发布说明和历史经验；
- 是否存在散落在根目录或自定义目录中的非规范文档；
- 已有文档、配置与当前代码是否互相一致。

### 2. 判断当前治理状态

本 skill 会使用以下状态描述项目，而不是简单判断“有没有文档”：

| 状态 | 含义 | 通常下一步 |
| --- | --- | --- |
| 尚未初始化 `uninitialized` | 没有可靠的 Agent 工作入口 | 建立最小控制入口 |
| 已发现可复用材料 `discovered` | 有现有文档，但尚未整理到标准责任位置 | 提取和映射现有内容 |
| 采用中 `adopting` | 已有治理入口，但仍有适用能力未完成 | 继续最小迁移切片 |
| 已符合要求 `conformant` | 适用能力存在且通过审计 | 按已有入口工作并按需复审 |
| 已退化 `degraded` | 文档、状态、命令或路径已经缺失/失效/冲突 | 先修复治理基线再继续信任其指导 |

### 3. 根据风险决定治理深度

项目不需要自行挑选复杂的内部配置档位。Agent 会根据仓库事实解释推荐的深度：

| 项目特征 | 通常需要的能力 |
| --- | --- |
| 小型库或维护型工具，Agent 主要修改代码并提交 | 入口规则、manifest、经验反馈、测试与 Git 流程 |
| 持续接收需求和迭代开发的产品 | 以上能力加文档地图、backlog、iteration、需求进入、变更控制和稳定事实 |
| 涉及生产发布、权限、数据、外部执行或重大集成风险 | 以上能力加决策、路线图、发布/审查及风险专属门禁 |

### 4. 说明方案后再落地

在仅要求分析或审计时，skill 会说明：

- 当前治理状态；
- 已有资产中值得保留的内容；
- 哪些缺口可能导致真实错误；
- 推荐的目标结构与最小下一步；
- 实施时会创建、修改、提取或保留哪些文件。

除非用户已经明确要求实施，否则不会在诊断阶段直接重写目标项目的治理文档。

### 5. 修改后验证

治理文件修改完成后，Agent 应检查：

- manifest 声明的入口和能力是否有真实文件支撑；
- `AGENTS.md` 的路由是否能到达必要流程；
- 文档链接是否断裂；
- 文档中的源码路径、命令和稳定事实是否仍符合当前仓库；
- 已有非规范文档中的有效内容是否已经被正确提取或登记迁移；
- 完成状态是否有真实命令输出或具体人工验证证据支撑。

## 标准文档结构

持续开发的产品型项目通常逐步收敛到以下结构；较小项目可以只启用适用部分。

```text
project-root/
├── AGENTS.md
├── EVOLUTION.md
├── .agent-governance/
│   └── manifest.yaml
└── docs/
    ├── README.md
    ├── backlog/
    │   └── PRODUCT-BACKLOG.md
    ├── iterations/
    │   └── README.md
    ├── decisions/
    │   └── README.md
    ├── roadmap/
    ├── proposals/
    ├── reference/
    └── sop/
```

### 每类文档负责什么

| 位置 | 写什么 | 不应写什么 |
| --- | --- | --- |
| `AGENTS.md` | 开工前必须看到的规则、任务路由、已知陷阱、收尾检查 | 大段历史背景或完整操作教程 |
| `.agent-governance/manifest.yaml` | 状态、入口、能力、风险门禁和迁移映射 | SOP 具体内容的重复副本 |
| `EVOLUTION.md` | 已发生问题的现象、原因、修复和预防办法 | 普通版本变更流水账 |
| `docs/README.md` | 文档导航与归档规则 | 某一功能的详细设计 |
| `docs/reference/` | 当前稳定技术事实与契约 | 执行进度或临时计划 |
| `docs/sop/` | 重复任务的步骤与验证标准 | 会随代码事实变化而漂移的重复说明 |
| `docs/backlog/` | 已准备评估或执行的需求、缺陷和技术债 | 尚未成熟的随手想法 |
| `docs/iterations/` | 一次工作周期选了什么、做了什么、如何验证 | 唯一的产品需求事实来源 |
| `docs/decisions/` | 有影响范围和替代方案的重要决策 | 普通代码修改记录 |
| `docs/roadmap/` | 阶段方向、依赖和优先顺序 | 当前 story 的执行明细 |
| `docs/proposals/` | 暂未成为可执行任务的想法 | Agent 可直接开工的任务 |
| `docs/archive/` | 仍需保留的历史快照和已过期材料 | 当前必须遵守的规则 |

### `AGENTS.md` 的最低要求

对由 Agent 持续修改代码的产品型项目，`AGENTS.md` 至少应包含：

- **Hard Constraints**：修改前查看工作树、先按路由读取流程、需求/变更/经验/决策如何归口，以及项目特有禁令。
- **Git Rules**：如何暂存和检查差异、提交格式、是否要求标明模型来源。
- **Task Router**：新需求、迭代启动、迭代中变更、开发、测试、排错、文档整理和决策应先读什么。
- **Session End Checklist**：状态是否更新、验证是否执行、经验或 ADR 是否遗漏、提交是否准备完成。
- **Current Known Traps**：如已有会重复引发错误的项目特定陷阱，应明确写出。

### 常见流程文件何时需要

| 流程文件 | 应建立的条件 |
| --- | --- |
| `START-ITERATION.md` 与 `ITERATION-WORKFLOW.md` | 项目已经存在迭代记录，或采用计划式功能开发 |
| `CHANGE-CONTROL.md` | 开发中会接收需求变化，或项目属于持续产品开发 |
| `LOCAL-DEV.md` | Agent 需要在本地启动或调试项目 |
| `NEW-FEATURE.md` | Agent 会持续新增产品能力 |
| `DOC-CHECK.md` | 项目有多层治理文档，或正在迁移旧文档 |
| `RELEASE.md` | Agent 参与构建产物、发布或部署验证 |
| 风险专属 SOP | 存在 API 合约、数据库迁移、权限、安全、外部调用等明确风险时 |

## 已有文档如何迁移

初始化不是创建一套平行的新文档。如果目标项目已经有说明材料，但文件位置不规范或一个文件混合多种职责，skill 会将仍有效的内容拆分到标准位置，同时保留来源和历史。

### 迁移原则

1. **先盘点，不先覆盖**：识别每个旧文档包含哪些规则、事实、决策、任务或历史记录。
2. **先验证是否仍有效**：与当前代码、配置和更新的文档冲突的内容，不会被直接迁移成当前规则。
3. **按职责提取**：有效内容进入标准位置，而不是只建立空目录或留下一个链接。
4. **保留可追溯性**：原文档可以保留、归档或明确标注被替代；有价值的历史不会静默删除。
5. **记录迁移关系**：manifest 会记录来源、提取目标和迁移状态。
6. **最终可导航**：Agent 日常执行不应依赖先翻找任意旧文档，活跃规则必须能从标准入口找到。

### 内容归位示例

| 旧文档中的内容 | 提取到哪里 |
| --- | --- |
| 对 Agent 的强制规则、禁止事项、任务导航 | `AGENTS.md` |
| 项目当前架构、目录职责、有效命令、配置边界 | `docs/reference/` |
| 反复执行的测试、发布、需求评审或迁移步骤 | `docs/sop/` |
| 可实施的需求、缺陷或技术债 | `docs/backlog/` |
| 一次迭代的执行记录与验证结果 | `docs/iterations/` |
| 技术路线或部署形态的重大取舍 | `docs/decisions/` |
| 已确定的阶段顺序或长期方向 | `docs/roadmap/` |
| 未成熟的候选方向 | `docs/proposals/` |
| 已发生故障带来的可复用教训 | `EVOLUTION.md` |
| 已完成或不再有效但需要保留的计划 | `docs/archive/` |

例如，一个旧的“框架迁移总结”可能同时包含当前目录结构、为何移除旧依赖、迁移中踩过的坑和未来清理任务。初始化时这些内容应分别进入 `docs/reference/`、`docs/decisions/`、`EVOLUTION.md` 与 `docs/backlog/`，旧总结本身则可归档并在 manifest 中留下映射。

## 风险与门禁

本 skill 不会仅根据目录名称生成风险流程，而是根据项目可观察事实推导检查项。例如：

| 项目特征 | 需要防止的问题 | 可能产生的治理门禁 |
| --- | --- | --- |
| Agent 会修改代码并提交 | 无关改动混入提交或无法追溯 | 修改前检查工作树、提交前检查 staged diff、定义提交规则 |
| 前端与后端通过 API 协作 | 接口字段或路径不一致 | 合约和调用方同步检查、相关测试 |
| 有认证、权限或租户隔离 | 访问控制绕过 | 权限矩阵、公开/保护路由验证 |
| 有 Docker、代理或静态资源交付 | 本地通过但部署失败 | 构建产物、代理路径与发布验证 |
| 调用方可触发外部 HTTP 请求、工具或 webhook | 匿名执行、上游失败被当成成功、响应无限扩大 | 明确执行授权、超时/大小/错误处理、可控本地测试 |
| 文档记录 story 完成状态 | 勾选完成但未真正执行必要验证 | 要求记录实际命令与结果，高风险任务完成前独立审查 |

没有事实支撑的高成本流程不应被强行加入；已经发生或后果严重的风险，也不应只停留在说明文字中。

## 如何使用

### 只审计，不修改项目

适合先了解现状、判断是否值得建设治理体系：

```text
使用 $agent-project-governance 审计当前项目的 Agent 治理状态。
只分析，不修改文件。说明已有资产、实际风险、主要缺口和推荐的最小下一步。
```

### 初始化一个尚未治理的项目

```text
使用 $agent-project-governance 为当前项目初始化 Agent 工程治理。
先读取代码和现有文档，说明建议结构及会保留/提取/创建的内容，再开始实施。
```

### 整理已有但分散的治理文档

```text
使用 $agent-project-governance 将当前项目已有的规则、计划、技术决策和经验文档迁移到规范结构。
不要删除有价值历史；在 manifest 中记录来源到目标的映射。
```

### 修复已经退化的治理结构

```text
使用 $agent-project-governance 检查当前治理文档与源码、命令和 manifest 是否一致。
如果属于 degraded 状态，修复最小必要基线并说明仍待完成的能力。
```

### 把真实故障写回治理

```text
使用 $agent-project-governance 分析这次缺陷或发布失败暴露的流程问题。
将可复用教训写回 EVOLUTION.md，并判断是否需要更新 AGENTS.md、SOP 或风险门禁。
```

## 如何验证结果

本 skill 附带基础一致性校验器。目标项目已建立 manifest 后，在本 skill 目录中运行它，并将目标项目路径作为参数。例如：

```bash
python3 scripts/validate_project_governance.py /path/to/your-project
```

校验器会检查：

- `.agent-governance/manifest.yaml` 是否存在，声明的入口路径是否有效；
- 产品型项目是否错误地将迭代或变更控制标记为不适用；
- 已声明 `conformant` 的能力是否有对应文件和入口路由；
- `AGENTS.md` 是否具备必要执行区段；
- Markdown 本地链接是否断裂；
- 活跃治理文档是否仍引用已删除的明确 `src/...` 源码路径。

校验器用于发现结构性和明确引用问题；它不能代替对业务需求、架构正确性、安全设计或实际运行结果的人工/Agent 审查。

## 使用边界

- 本 skill 负责工程治理文档、入口、状态和校验规则，不自动替团队决定产品方向。
- 不因为其他项目有某份 SOP，就假定目标项目也需要同样内容。
- 不将文件“存在”误认为流程“有效”；内容必须与当前代码和实际验证证据一致。
- 不将非规范旧文档静默删除，也不允许其中仍有效的规则永远滞留在标准入口之外。
- 不把勾选框或口头结论当作完成证据；需要验证的任务应记录真实执行结果。

## 常见问题

### 这会修改业务代码吗？

治理初始化或审计通常只修改 `AGENTS.md`、`EVOLUTION.md`、`.agent-governance/` 和 `docs/` 等治理资产。除非用户另行要求修复被治理审计发现的业务或配置问题，否则不会以建立文档为名修改产品行为。

### 已经有 `AGENTS.md`，还需要使用吗？

可能需要。`AGENTS.md` 存在并不能证明它覆盖了当前命令、风险和流程，也不能证明它链接到的 SOP 仍然存在。本 skill 可以审计其是否可执行、是否过期，以及是否与 manifest 和代码一致。

### 是否一定要创建完整目录树？

不一定。小型项目只需要安全协作真正依赖的能力。持续产品开发或高风险系统才应逐步具备较完整的文档分层和流程门禁。

### 原有文档会被删除吗？

不会静默删除。有效内容会被提取到标准位置，历史内容会被保留或归档，替代关系会被明确记录。若需要删除或大规模重组，应由用户确认。

### 为什么需要 manifest？

它让治理本身可审计：项目声明采用了哪些能力、哪些尚未完成、哪些已经失效，以及旧文档被提取到了哪里。这样 Agent 不会因为看到某个文件名就误以为流程已经可靠存在。
