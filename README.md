# Agent Project Governance

让 AI Agent 真正遵守工程规则——不是写在文档里没人看的那种，而是 Agent 每次开工前都会检查、每次完成后都会验证的那种。

---

## 它解决什么问题

你让 AI Agent 帮你写代码，但迟早会遇到这些情况：

- Agent 改了不该改的地方，因为它不知道项目里有哪些禁区
- 项目文档写着"跑测试再提交"，但测试命令早就过期了
- 上次踩过的坑，这次又踩了一遍
- 计划做 A，做着做着变成了 B，回头看分不清"原来打算做什么"和"实际做了什么"
- 一个大需求直接开工，做着做着发现做不完

这些问题背后的原因是一样的：**项目从来没有给 Agent 写过一份它能读懂、会遵守的规矩。**

`agent-project-governance` 就是做这件事的。它会检查你的项目现状，然后建立一套 Agent 能找到、能照着做、能验证结果的规则体系。

## 核心特性

### 🎯 治理规则真正能生效

传统敏捷实践（Scrum、XP、BDD）的规则写得很好，但人对规则的遵守是不可靠的——嫌麻烦就跳过，忙起来就忘掉。AI Agent 不一样：它不会偷懒，不会嫌烦，不会觉得"这次应该没事"就跳过检查。

| 过去为什么做不到 | 现在怎么解决 |
| --- | --- |
| **迭代计划容易被覆盖**——做着做着就改计划，事后分不清"原来打算做什么"和"实际做了什么" | Agent 把提交的计划当作基线保护起来，执行结果追加在后面，不直接覆盖（迭代基线完整性） |
| **Definition of Done 流于形式**——勾选了"已测试"但其实没跑 | Agent 必须记录真实的命令输出和验证结果，不能只打勾（DoD 可验证化） |
| **变更控制太麻烦**——改个需求要走流程，人嫌烦就跳过了 | Agent 接到需求变化时自动走变更登记，不增加人的工作量（轻量变更控制） |
| **BDD 验收条件没人写**——Story 只有一句话，什么叫"做完"全靠猜 | Agent 按 Given/When/Then 格式自动补齐验收条件，人和 Agent 都能验证（BDD 验收） |
| **经验教训没人写回**——踩过的坑下次照样踩 | Agent 把故障分析自动写入经验记录，并检查是否需要更新规则（持续改进 / Kaizen） |
| **新迭代不看旧状态**——上轮还没收尾就开新轮子 | Agent 开始新迭代前必须先盘点所有未完成的旧迭代（WIP 限制） |
| **大需求直接开工**——把"重构整个认证系统"当一条任务做 | Agent 自动拆解为 Epic 和可独立验收的 Story（需求拆解） |

### 🔍 先诊断，再开药

不会一上来就给你套模板。Agent 会先读你的项目：技术栈、构建工具、测试命令、有没有认证/权限/数据库等高风险边界、已有文档是否还和代码对得上。然后只建立项目真正需要的规则。

### 📊 五级治理状态

项目不是简单的"有文档/没文档"，而是处于以下某个状态：

| 状态 | 含义 | 通常下一步 |
| --- | --- | --- |
| `uninitialized` | 没有 Agent 能用的规矩 | 建立最小控制入口 |
| `discovered` | 有零散文档，但没整理到标准位置 | 提取和映射现有内容 |
| `adopting` | 治理框架已建立，但还有内容没迁移完 | 继续迁移剩余内容 |
| `conformant` | 规则齐全且经过验证 | 按已有规则工作 |
| `degraded` | 文档过期、命令失效或状态矛盾 | 先修复基线再继续 |

### ⚖️ 按风险决定治理深度

你不需要自己选"轻量/标准/完整"模式。Agent 会根据项目实际情况推荐：

| 项目类型 | 通常需要的规则 |
| --- | --- |
| 小型库，Agent 只改代码和提交 | 入口规则、manifest、经验反馈、测试与 Git 流程 |
| 持续迭代的产品 | 以上 + 文档地图、backlog、迭代流程、变更控制 |
| 涉及生产发布、权限、数据或外部服务 | 以上 + 决策记录、发布审查、风险专属门禁 |

### ✅ 完成有标准，不是文件建了就算

这是从 XP 的"做完的定义"来的：文件建了不等于规矩生效。比如 `AGENTS.md` 里写了"跑测试再提交"，但测试命令过期了，这条规则就是废的。

每次实施完成后，Agent 会给出明确的交付结论：

- **`complete`** — 计划要做的都做完了，验证通过，遗留事项已登记
- **`partial`** — 产出了有用结果，但还有未完成的工作
- **`blocked`** — 遇到缺少权限或决策，当前无法继续

### 🛡️ 根据实际风险生成检查项

不是照着目录名猜你需要什么流程，而是看你项目里实际用了什么技术、有什么风险。比如：

| 项目特征 | 可能出的错 | 加什么检查 |
| --- | --- | --- |
| Agent 会提交代码 | 无关改动混入 | 提交前检查 staged diff |
| 前后端通过 API 协作 | 接口不一致 | 合约同步检查 |
| 有认证和权限 | 访问控制绕过 | 权限矩阵、路由验证 |
| 有 Docker 或代理 | 本地通过但部署失败 | 构建产物和发布验证 |
| 调用外部服务 | 上游失败被当成功 | 超时处理、可控本地测试 |

### 🔁 内置校验器

附带一个 Python 脚本，可以随时检查治理产物是否还靠谱：

```bash
python3 scripts/validate_project_governance.py /path/to/your-project
```

检查内容：manifest 声明的文件是否存在、`AGENTS.md` 是否有必要的区段、链接是否断裂、文档是否引用了已删除的源码路径等。

## Quick Start

### 审计项目现状

先了解情况，不改文件：

```text
使用 $agent-project-governance 审计当前项目的 Agent 治理状态。
只分析，不修改文件。说明已有资产、实际风险、主要缺口和推荐的最小下一步。
```

### 初始化治理

```text
使用 $agent-project-governance 为当前项目初始化 Agent 工程治理。
先读取代码和现有文档，说明建议结构及会保留/提取/创建的内容，再开始实施。
```

### 整理已有文档

```text
使用 $agent-project-governance 将当前项目已有的规则、计划、技术决策和经验文档迁移到规范结构。
不要删除有价值历史；在 manifest 中记录来源到目标的映射。
```

### 其他用法

| 场景 | 怎么用 |
| --- | --- |
| 治理结构已经退化 | `$agent-project-governance 检查当前治理文档与源码、命令和 manifest 是否一致` |
| 发生了故障或回归 | `$agent-project-governance 分析缺陷暴露的流程问题，将教训写回 EVOLUTION.md` |
| 大需求需要拆解 | `$agent-project-governance 检查 backlog 中的大型需求，拆为 Epic 和可执行 Story` |
| 准备下一轮迭代 | `$agent-project-governance 先盘点所有未完成迭代，再从 backlog 选择新的 Ready Story` |

## 标准文档结构

持续开发的产品型项目通常会收敛到以下结构（小项目只用其中一部分）：

```text
project-root/
├── AGENTS.md              # Agent 开工前必须看的规则
├── EVOLUTION.md           # 踩过的坑和教训
├── .agent-governance/
│   └── manifest.yaml      # 治理状态和能力清单
└── docs/
    ├── README.md          # 文档导航
    ├── backlog/           # 需求池（Epic / Story）
    ├── iterations/        # 迭代计划和执行记录
    ├── decisions/         # 重大决策记录（ADR）
    ├── roadmap/           # 阶段方向
    ├── proposals/         # 未成熟的想法
    ├── reference/         # 稳定的技术事实
    ├── sop/               # 可重复执行的流程
    └── archive/           # 历史快照
```

### 每个文件负责什么

| 文件 | 写什么 | 不写什么 |
| --- | --- | --- |
| `AGENTS.md` | 开工前必须看到的规则、任务路由、已知陷阱 | 大段历史或完整教程 |
| `manifest.yaml` | 状态、能力清单、风险门禁 | SOP 内容的副本 |
| `EVOLUTION.md` | 问题现象、原因、修复和预防办法 | 版本变更流水账 |
| `docs/sop/` | 反复执行的流程步骤和验证标准 | 会随代码漂移的说明 |
| `docs/backlog/` | 准备好执行的需求、缺陷和技术债 | 随手想法 |
| `docs/iterations/` | 迭代基线、执行记录和验证证据 | 产品需求详情 |
| `docs/decisions/` | 重大取舍和替代方案 | 普通代码修改记录 |

### `AGENTS.md` 至少包含什么

由 Agent 持续修改代码的项目，`AGENTS.md` 至少应有：

- **Hard Constraints** — 修改前检查工作树、项目禁令
- **Git Rules** — 提交格式、暂存检查
- **Task Router** — 不同类型的任务先读什么
- **Session End Checklist** — 状态是否更新、验证是否执行
- **Current Known Traps** — 项目特有的重复陷阱

## 需求拆解

> _来自 Scrum 的 Epic/Story 拆分和 XP 的小步交付原则_

大需求不会被直接当任务开工。比如"建立统一身份权限能力"是一个 Epic，"为管理端接口增加角色校验并验证未授权响应"是一个 Story。

拆解规则：
- 每个 Story 能独立验证，不会跨多个迭代
- Story 引用所属 Epic，Epic 维护子项状态
- 迭代只选已经准备好的 Story，不拿大 Epic 硬上
- 能独立验收的需求即使涉及前后端+文档，也不必硬拆

## 迭代计划保护

> _来自 Scrum 的 Sprint 计划完整性和精益的"不覆盖历史"原则_

已提交的迭代计划就是基线。执行结果追加在后面，不会用"实际做了什么"去覆盖"原来打算做什么"。

开始新迭代前，必须先处理现有迭代的未完成状态：

| 现有状态 | 先做什么 |
| --- | --- |
| Active / In Progress | 继续完成，或记录为何暂停 |
| Review | 补齐验收证据 |
| Planned | 激活原计划，或记录延期原因 |
| Blocked | 确认阻塞原因并记录结论 |

## 已有文档迁移

> _来自精益的"尊重现有价值"原则_

如果项目已有文档但位置不规范，不会创建一套平行的新文档。而是：

1. **先盘点** — 识别每个旧文档包含什么
2. **验证是否有效** — 过期内容不迁移成规则
3. **按职责提取** — 有效内容进入标准位置
4. **保留历史** — 旧文档可归档，不静默删除
5. **记录映射** — manifest 记录来源和迁移状态

## 这个 Skill 不会做的事

- 不会替你决定产品方向——只负责工程规则
- 不会照搬别的项目的流程——每个项目只建它真正需要的
- 不会因为文件"存在"就认为流程"有效"——内容和代码必须一致
- 不会静默删除你的旧文档——有效内容提取到标准位置，历史保留或归档
- 不会把打勾当完成证据——必须记录真实执行结果
- 不会覆盖已发布的迭代计划
- 不会把没拆解的大 Epic 当一次能做完的任务

## 常见问题

### 这是给谁用的？

给那些已经让 AI Agent（比如 Cursor、Claude Code、Copilot、OpenCode 等）参与项目开发，并且希望 Agent 能长期、可靠地维护项目的人。如果你只是偶尔让 AI 改个 bug，不需要这套完整的治理体系。

### 这会修改业务代码吗？

不会。治理初始化或审计只修改 `AGENTS.md`、`EVOLUTION.md`、`.agent-governance/` 和 `docs/` 等治理文件。除非你另行要求，否则不会以建立文档为名修改产品代码。

### 已经有 `AGENTS.md`，还需要用吗？

可能需要。`AGENTS.md` 存在不能证明它覆盖了当前命令、风险和流程，也不能证明它链接到的 SOP 还存在。这个 skill 可以审计它是否可执行、是否过期。

### 是否一定要创建完整目录树？

不一定。小型项目只需要真正依赖的规则。持续产品开发或高风险系统才需要较完整的文档分层。

### 原有文档会被删除吗？

不会静默删除。有效内容会被提取到标准位置，历史内容会被保留或归档。需要删除时由你确认。

### 为什么需要 manifest？

它让治理本身可审计：哪些能力已具备、哪些已失效、旧文档被提取到了哪里。这样 Agent 不会因为看到某个文件名就误以为流程已经存在。

### 已计划的迭代临时不做了，可以直接改成新任务吗？

不能直接覆盖。应保留原计划内容，记录延期或替代原因，为新目标建立新的迭代记录。

### Epic 和 Story 是强制的吗？

不是。只有需求包含多个可分别验收的结果、需要跨阶段交付时才需要拆分。能独立交付和验证的单一需求，直接作为 Story 管理。

## 理论依据

本 skill 的设计借鉴了以下方法论，但不是照搬理论——而是提取其中"过去对人要求太高，现在 Agent 能做到"的部分：

| 方法论 | 借鉴了什么 | 在哪里体现 |
| --- | --- | --- |
| **Scrum** | Sprint 计划基线保护、迭代盘点、Epic/Story 拆分、Definition of Done | 迭代计划保护、需求拆解、交付结论 |
| **XP（极限编程）** | 小步交付、持续集成验证、集体代码所有权下的规则共享 | 治理深度分级、验证检查项 |
| **BDD（行为驱动开发）** | Given/When/Then 验收条件 | Story 验收标准 |
| **精益（Lean）** | 消除浪费、尊重现有价值、持续改进（Kaizen） | 文档迁移原则、EVOLUTION.md 经验写回 |
| **变更控制** | 需求变化的登记和影响评估 | CHANGE-CONTROL SOP |
| **ADR（架构决策记录）** | 重大取舍的记录 | docs/decisions/ |
| **WIP 限制** | 同时进行的工作项有上限 | 新迭代前的旧迭代盘点 |
